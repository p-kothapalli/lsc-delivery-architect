Inside the Skill

Seventeen rules, a seven-step pipeline, and a validator that runs before you see anything.

Every rule in the skill carries its own stated rationale — the because clause is written into the rule, not left implied. That is what makes the behaviour predictable enough to argue with. This tab is the whole mechanism, unabridged.

STEP 0–6

The pipeline every request goes through

Steps are not optional, but the mode decides which ones do real work. STEP 3 is where grounding happens and STEP 5 is where the skill checks its own output — both run whether or not you asked for them.

STEP 0

Workflow detection

Maps your phrasing to one of six modes, which then determines the question phases and the output contract. Ambiguous input defaults to New Feature and asks rather than guessing.

NuanceNatural language always works; the prompt templates are optional accelerators, not required syntax.
STEP 1

Sub-domain selection

Commercial, Medical, Market Access, Cross-domain / Platform, or Custom. Five options, not three — the cross-domain option exists for shared Account, Consent, and Data Cloud work that belongs to no single vertical.

Why firstEach sub-domain names different objects and personas. Wrong sub-domain produces a story that is unbuildable, not merely inaccurate.
STEP 2

Clarifying questions — question-first

Four phases, minimum 5 and maximum 16 questions, delivered through the AskQuestion tool as a structured picker rather than prose.

NuanceThe floor of 5 matters as much as the ceiling of 16 — it is what stops a detailed-looking prompt from bypassing discovery.
STEP 3

Codebase & docs analysis — graph-first

Custom components resolve through code-review-graph; standard LSC objects through salesforce-docs. Grep and Glob are the fallback, not the first move.

OrderingMandated by a separate workspace rule, code-review-graph-first.mdc — not by this skill alone.
STEP 4

Generate

Produces the artifact in the canonical section order from output-template.md. In Plan + Prototype mode this step produces a Solution Plan and prototype instead of a story.

NuanceSection order is fixed on purpose so developers and QA find ACs, effort, and impact in the same place every time.
STEP 5

Review & iterate — the validator loop

Ten checks run against the draft, and failures are fixed before the artifact is presented to you. Four of the ten are hard blockers that stop presentation outright.

ImplicationIf a blocker reaches your screen, the loop did not run — which usually means the skill is not actually loaded.
STEP 6

Post-generation offers

Seven optional next steps, offered only where the underlying MCP server or CLI is actually connected — it verifies availability first rather than offering something that will fail.

Nuance§6.7, the grounded product-owner prototype, lives here — which is why you can request it after a story, not only before one.

The distinction worth internalising

Plan + Prototype drops the story blockers — Pattern A, Pattern E, Technical Implementation, Definition of Done — because its deliverable is a plan. It does not drop the grounding blockers: the build-technology decision must still be stated, every prototype element must still be labelled, and no component name may be invented. A "lighter" mode is not a licence to guess.

Naming & styling nuances

Three specifics that are easy to get wrong

Terminology

It is Omnistudio Data Mapper

"DataRaptor" is the legacy name. Writing it in new story prose is an explicit stop condition. The skill will correct it — and so should you in review.

Runtime

Standard, not managed-package

New OmniStudio work defaults to the Standard runtime — native objects, Salesforce CLI deployable, Agentforce-ready. The managed-package Vlocity runtime is maintenance-mode. A verdict that omits the runtime is incomplete.

Prototype CSS

The primer is mandatory

Hand-rolled SLDS-flavoured CSS is non-compliant. Every prototype opens with the primer's :root variable block, uses its utility classes and blueprint recipes, applies the .lsc-badge overlay, and records a self-check score in a header comment.

The badge classes on a compliant prototype are literal: .lsc-badge.ootb, .config, .flow, .lwc, .os, .apex, .ext. If you are reviewing a prototype and the badges are ad-hoc spans, it was not built against the primer.

Artifact Contract

What the artifact guarantees — and what you are accountable for.

You sign the output, not the agent. This is what the contract promises, expressed precisely enough that you can tell when it has been broken.

The five AC patterns

Every acceptance criterion uses exactly one of these

Neither a GWT shape nor a field table fits everything. Picking the wrong pattern is the most common quality problem in a story that otherwise passes every blocker — do not force Given/When/Then onto a metadata spec.

Pattern A · default

Behavioural

Given / When / Then. Use for anything the persona can observe: a record is created, a field changes, an error appears, inventory moves, routing happens.

Business verbs only — "the on-hand balance is reduced," never "Quantity__c is decremented."

Pattern B

Field / object / metadata

New custom fields, objects, Custom Metadata Types. A specification table, not a behaviour — so it does not take a GWT shape.

Pattern C

Permission set / FLS

Who can see and edit what. Pairs with Pattern B whenever fields are added — and with the Definition of Done gate on access.

Pattern D

Field update rules

Business calculation tables. Use when the requirement is a matrix of input conditions to resulting values rather than a single observable outcome.

Pattern E · mandatory

Record & field specification

Required on every outcome where records are created or updated. One block per object, every field, exact value, parents before children.

Rule of thumb

Pair A with E

Pattern A says "the sample drop is recorded." That does not tell a developer Status = Submitted. Whenever an A outcome writes records, an E block must sit beside it.

Pattern E anatomy

This is what "no follow-up meeting" looks like

One sub-block per object, in creation order. Every field enumerated with its exact value or formula, so a developer can build the write and QA can assert each field without translating anything.

The HCP trap — LSC-specific

An HCP, HCO, KOL, or DOL is the subject of the work, not the login role. "As an HCP, I want to receive a sample" is wrong: the rep is the one using Salesforce. Getting this backwards produces a story nobody can build a permission set for.

Definition of Done

Verifiable outcomes, not activities

Five gates, each conditional on what the story actually changed. A DoD that lists activities ("build the flow") instead of outcomes is a failed DoD.

GateApplies when
Primary happy-path behaviour verified in the target orgAlways
Key edge case or negative path verified against its ACAlways — the edge case is mandatory, not optional

≥ 85% Apex test coverage, including bulk and negative pathsApex changed
No regression to the flows named in Impact AnalysisAlways — and it is why Refactor mode names components

Repair & Review

When the output misses a blocker, fix it with a prompt — not by hand.

Editing a bad artifact yourself hides the failure and you will hit it again next sprint. Naming the blocker back to the agent repairs the artifact and tells you whether the contract is loaded at all.

Eight failures, and the prompt that fixes each

If several of these fire at once, stop repairing and check the install — it usually means the trigger rule never landed in .cursor/rules/, or the window was not reloaded after you copied it.

Common mistakes

The rationalisations, and the rebuttal to each

The skill ships a table of the excuses that precede a contract violation. It is aimed at the agent, but it is just as useful pointed at a review conversation — every one of these is an argument you will eventually have with a teammate.

The excuseThe reality
"The HCP is the user, so 'As an HCP' is fine." HCP, HCO, KOL, and DOL are the subjects of the work. The persona is the Salesforce login user — Field Sales Rep, MSL, KAM. Use an HCP persona only for a genuine HCP-facing portal story. RULE 12
"This story is small — 'the user' is a fine persona." The persona contract is a hard blocker. Every "As a…" needs a concrete LSC business role, regardless of story size. RULE 12
"One Apex class or field API name inside the AC is harmless context." The business-language contract is a hard blocker. Move it to Technical Implementation — that is what the section is for. RULE 13
"LSC objects are standard — I'm sure of the field name." Verify standard objects and fields through salesforce-docs. Where the LSC package is not deployed, mark components proposed rather than asserting them. RULE 3 · 3a
"The Veeva term maps obviously — I'll keep the Veeva wording." Migration mode must translate to LSC-native terminology. The Veeva term survives only in a mapping note, never in the story body. STEP 0
"The prompt is detailed enough — I'll skip clarifying questions." Question-first is non-negotiable. A detailed-looking prompt is exactly the case the 5-question floor exists for. RULE 2
"Given/When/Then is verbose — I'll write prose ACs." Pattern A requires three explicit lines with a single When. Prose is not executable by QA. RULE 11
"The ACs describe it — I'll drop the Technical Implementation section." Every story carries it, after the ACs. RULE 14

Two prompts on a cadence

The object catalog drifts with every release, and a reference edit can silently break a blocker. Both are cheap to check now and expensive to discover in a sprint.

Per release — catalog drift

Prompt
Review the LSC standard-object catalog reference against the current API version. What objects or fields have been added, renamed, or deprecated since Summer '26 / v67.0?

Quarterly — did a blocker break?

Prompt
Run each scenario in evaluations/ against this skill and score the output on every expected_behavior item. Report which blockers failed.
