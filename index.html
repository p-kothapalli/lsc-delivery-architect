Artifact Contract

What the artifact guarantees — and what you are accountable for.

You sign the output, not the agent. This is what the contract promises, expressed precisely enough that you can tell when it has been broken.

The five AC patterns

Every acceptance criterion uses exactly one of these

Neither a GWT shape nor a field table fits everything. Picking the wrong pattern is the most common quality problem in a story that otherwise passes every blocker — do not force Given/When/Then onto a metadata spec.

Pattern A · default

Behavioural

Given / When / Then. Use for anything the persona can observe: a record is created, a field changes, an error appears, inventory moves, routing happens.

Business verbs only — "the on-hand balance is reduced," never "Quantity__c is decremented."

Pattern B

Field / object / metadata

New custom fields, objects, Custom Metadata Types. A specification table, not a behaviour — so it does not take a GWT shape.

Pattern C

Permission set / FLS

Who can see and edit what. Pairs with Pattern B whenever fields are added — and with the Definition of Done gate on access.

Pattern D

Field update rules

Business calculation tables. Use when the requirement is a matrix of input conditions to resulting values rather than a single observable outcome.

Pattern E · mandatory

Record & field specification

Required on every outcome where records are created or updated. One block per object, every field, exact value, parents before children.

Rule of thumb

Pair A with E

Pattern A says "the sample drop is recorded." That does not tell a developer Status = Submitted. Whenever an A outcome writes records, an E block must sit beside it.

Pattern E anatomy

This is what "no follow-up meeting" looks like

One sub-block per object, in creation order. Every field enumerated with its exact value or formula, so a developer can build the write and QA can assert each field without translating anything.

The HCP trap — LSC-specific

An HCP, HCO, KOL, or DOL is the subject of the work, not the login role. "As an HCP, I want to receive a sample" is wrong: the rep is the one using Salesforce. Getting this backwards produces a story nobody can build a permission set for.

Definition of Done

Verifiable outcomes, not activities

Five gates, each conditional on what the story actually changed. A DoD that lists activities ("build the flow") instead of outcomes is a failed DoD.

GateApplies when
Primary happy-path behaviour verified in the target orgAlways
Key edge case or negative path verified against its ACAlways — the edge case is mandatory, not optional
New fields and objects deployed with FLS applied per the permission-set ACFields or objects changed
≥ 85% Apex test coverage, including bulk and negative pathsApex changed
No regression to the flows named in Impact AnalysisAlways — and it is why Refactor mode names components

Runtime call, made once

Repair & Review

When the output misses a blocker, fix it with a prompt — not by hand.

Editing a bad artifact yourself hides the failure and you will hit it again next sprint. Naming the blocker back to the agent repairs the artifact and tells you whether the contract is loaded at all.

Symptom to repair

Eight failures, and the prompt that fixes each

If several of these fire at once, stop repairing and check the install — it usually means the trigger rule never landed in .cursor/rules/, or the window was not reloaded after you copied it.

SymptomLikely causeRepair
It wrote acceptance criteria after you said "no stories yet" STEP 0 routed to New Feature instead of Plan + Prototype Re-run in Plan + Prototype mode. Produce only the Solution Plan and the grounded prototype — no acceptance criteria, no field specs.
The persona is "the user" or "a business user" The persona blocker was not applied — often the rule file is missing The persona is not a concrete LSC business role. Re-anchor it to the persona cheatsheet and rewrite the story header.
An AC contains an Apex class, an IP step number, or a *__c field The business-language blocker was skipped Move every technical name out of the Given/When/Then lines into Technical Implementation, and restate each criterion in language a QA analyst can execute directly.
A "records are updated" outcome has no field table Pattern E missing — the single most common gap That outcome writes records but has no Pattern E block. Enumerate every object and every field with its exact value, parents before children. No "etc."
It chose OmniScript for a short three-field form The RULE 7a ladder was not walked Walk the declarative-first ladder explicitly. Show me why Dynamic Actions, Action Launcher, Field Sets, and Screen Flow were each insufficient before OmniScript.
It named an object or component you do not recognise Verification indexes unavailable, and it asserted anyway Which of the objects and components you named did you verify, and against what? Mark everything unverified as (proposed) and list what you could not confirm.
The prototype looks like a generic web app The §6.7 grounding rule was skipped Every interactive element needs the Salesforce component that will implement it, plus the build-technology banner and the footer legend. Re-issue it grounded.
It answers generically and never names a mode The rule is not in .cursor/rules/, or the window was not reloaded Which skill and rule are you applying to this request, and which workflow mode did you detect? — then reload the window if it cannot say.
The two repairs worth keeping to hand
Prompt · missing field spec
That outcome creates or updates records but has no Pattern E block. Enumerate every object and every field with its exact value, parents before children, one table per object. Remove any "and related fields are updated" phrasing.
Prompt · unjustified build tech
Walk the RULE 7a declarative-first ladder explicitly for this requirement. Show me why Dynamic Actions, Action Launcher, Field Sets, and Screen Flow were each insufficient before you reached for anything custom, and state the rejected alternative in the plan.

Keep it current

Two prompts on a cadence

The object catalog drifts with every release, and a reference edit can silently break a blocker. Both are cheap to check now and expensive to discover in a sprint.

Per release — catalog drift

Prompt
Review the LSC standard-object catalog reference against the current API version. What objects or fields have been added, renamed, or deprecated since Summer '26 / v67.0?

Quarterly — did a blocker break?

Prompt
Run each scenario in evaluations/ against this skill and score the output on every expected_behavior item. Report which blockers failed.

The evaluations are the source of truth, not the documentation. Extend them before you extend a reference — otherwise you have no way to tell whether the edit helped.
