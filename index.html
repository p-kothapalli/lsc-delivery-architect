Why It Exists

Every LSC engagement argues about the same two questions — and always too late.

A product owner is asked to sign Given/When/Then acceptance criteria before they have seen a screen or heard a build-technology decision. This skill inverts that order: plan and prototype first, stories second.

01

Stories arrive before shape

A Given/When/Then pack is signed before anyone has seen the screen. So the product owner hedges, and refinement becomes an argument about wording instead of about what gets built.

02

"Can we do this out of the box?"

The build-technology call — Dynamic Actions, Screen Flow, LWC, OmniScript — gets made after the estimate is committed. That is where the cost surprise lives.

03

Same ask, different stack

One architect defaults every guided flow to OmniScript, another to Screen Flow. The decision was never written down, so it is re-derived on every engagement.

What product owners actually ask first

"What will this look like on-screen — and can we build it with out-of-the-box Lightning, or do we need LWC / Flow / OmniStudio?"

Until those two questions are answered, Given/When/Then is theatre. The team is arguing about acceptance criteria for a shape nobody has agreed to.

The Shift

LSC delivery does not need more acceptance criteria. It needs the build made visible first.

Before anyone writes a Given/When/Then line, the product owner should be able to click the feature and see, on every control, whether it is standard Salesforce or something the team has to build.

Today

Stories first, mockup maybe, build technology decided last. Personas drift to "as a user," records are specified as "and related fields are updated," and the developer books a follow-up meeting before writing a line of code.

With the Delivery Architect

A Solution Plan and a grounded prototype land first, on a declarative-first build decision. Stories follow once the product owner has walked the mockup and agreed to the shape — with every field enumerated.

From the skill contract

"A prototype without the grounding is worse than no prototype — it misleads the product owner on cost shape. That is the whole point."

✦

The agent already knows the LSC personas, the ~350 standard objects, the Veeva translation, and the Concur expense model — so no architect starts from a blank page, and no one carries the standard alone. The time goes to the judgment calls only an architect can make.

Three artifacts — take any one, any combination, or all three
01

Solution Plan

Build-technology decision with its rejected alternative, component inventory with effort sizing, and open questions. Deliberately no ACs and no field specs — it is built for refinement before stories exist.

02

Grounded prototype

One self-contained .html file, SLDS 2 styling, clickable state toggles. Every element badged with the Salesforce component that will implement it.

03

Implementation-ready story

Concrete LSC persona, business-language Given/When/Then, a per-field record spec on every write, Technical Implementation table, Definition of Done, and effort sizing.

This is not a story generator with a mockup bolted on. It is a Delivery Architect that can stop at the plan, stop at the prototype, or continue to implementation-ready stories — on demand, independently.

STEP 0 · smart routing

Six modes, detected from how you phrase the ask

You never pick a template. STEP 0 reads the prompt, names the mode it detected, and changes both the question flow and the output contract to match. Phrase it in plain English and check that the mode it announces is the one you wanted.

ModeTriggered by phrasing likeWhat changes
Plan + Prototype "plan and prototype", "no stories yet", "prototype only" Phase 1–2 questions only, then a Solution Plan and a mockup. Story blockers deliberately skipped — no ACs are written.
New Feature "write a user story for…" Full Phase 1–4 question flow, then one complete story with Pattern A + E and an effort table.
Epic Breakdown "break down this spec", "decompose this scope doc" Proposes a decomposition for your approval first, then generates up to ten cross-referenced, dependency-ordered stories.
Refactor "change the existing…", "modify" Skips sub-domain selection and starts at technical discovery, anchored on a named existing component.
Bug Fix "defect", "broken", "fix" Skips the vertical questions entirely and focuses on current versus expected behaviour.
Veeva → LSC "migrate", "from Veeva", "this Veeva requirement" Translates every term to LSC-native wording and keeps the Veeva original in a source header only, never in the story body.
STEP 2 · question-first

What it asks you before it writes anything

Between five and sixteen questions, delivered as a structured multiple-choice picker rather than a wall of prose. The mode decides which phases run — Plan + Prototype stops after Phase 2. If it starts writing before asking, the contract is not being applied.

1

Context · all 3

Sub-domain, persona, and the business outcome. This is what stops the persona drifting to "as a user."

2

Business requirements · 3–5

Scope, regulatory constraints, and the records that must be written. Chosen by relevance, not asked mechanically.

3

Technical discovery · 3–5

Existing components, integrations, and org constraints. Skipped for Plan + Prototype; entered directly for Refactor.

4

Acceptance & validation · 2–3

Edge cases and how the outcome will be verified. Feeds the Definition of Done rather than being invented later.

Hard blockers — an artifact does not ship without these
The contract

Four things that must be true, and one thing it refuses to do

Must be true
  • Concrete LSC persona. Field Sales Representative, MSL, KAM, Event Organizer. Never "user." HCPs, HCOs, and KOLs are the subject of the work, not the login role.
  • Business-language Given/When/Then. Three explicit lines, one When. No Apex class names, OmniScript step numbers, SOQL, or API field names inside an AC — which is why QA can execute the criteria without a developer translating first.
  • Per-field record spec (Pattern E). Every "records are created or updated" outcome enumerates each object and each field with its exact value. Never "etc."
  • Technical Implementation after the ACs. The build-technology decision is stated with its rejected alternative, and prototype elements are labelled.
Will not invent
  • Custom components are verified through the code-review-graph index before they are named.
  • Standard LSC objects and fields are verified through salesforce-docs — ~350 objects, Summer '26 / API v67.0.
  • Anything unverifiable is written as (proposed) rather than asserted. A confidently wrong object name is the one error that survives all the way to a sprint commitment.
  • OmniScript is never the silent default. Dynamic Actions, Action Launcher, Screen Flow, and Field Sets are checked first.
RULE 7a · declarative-first

The build-technology ladder

The lowest-complexity option that actually meets the requirement wins. The chosen technology, the rationale, and the rejected alternative all go in the plan — so refinement stops arguing "should this be a flow?" and starts arguing scope.

Step 4 · artifact 3

What a developer receives once the plan is promoted

requirements/LSC_CompliantSampleDrop_UserStory.md

Compliant Sample Drop on a Visit

Persona: Field Sales Representative · Sub-domain: Commercial · Priority: P1

The story

As a Field Sales Representative, I want to record the samples I hand to a health care provider during a visit, so that the drop is captured against the correct lot and the provider's signature is on file before I leave the office.

Acceptance criteria — Pattern A

Given I am on a visit with a provider whose license is active
When I record a sample drop for a product lot that has stock on hand
Then the quantity I entered is accepted and the provider is asked to sign
And the remaining on-hand quantity for that lot is reduced by what I gave out

The edge case is mandatory, not optional

Given the lot I selected has fewer units on hand than I am trying to give out
When I enter the quantity
Then I am told how many units remain and cannot continue until the quantity fits

Business language is enforced

No Apex class name, OmniScript step number, SOQL query, or *__c API name appears inside any Given/When/Then line. All of it moves to Technical Implementation — which is why QA can execute these criteria without a developer translating first.

Persona Pattern A Pattern E field spec Tech Implementation Definition of Done Effort S–XXL

Pattern E — every field, no "etc."

Each object written by the story gets its own table: object, field, value, and source. A "and related fields are updated" outcome is treated as an incomplete story, because that sentence is where the follow-up meeting comes from.

Definition of Done and effort

A checkbox list covering profile and field-level access where fields changed, plus the ≥85% Apex coverage gate including bulk and negative paths if Apex changed. Effort is sized per component from S to XXL and always labelled AI-estimated — validate with team, because a number that looks authoritative is worse than one that admits it needs a human check.

Structure and contract are real; this excerpt is condensed. Full stories are written to requirements/.

Step 5 · the evidence it is governed

Same skill, two asks, two different verdicts

The stack is chosen because of the requirement, not because OmniStudio happened to be the house default. Both rationales are written into the plan.

Scenario A — Field Sales Representative

"Field reps need to hand out samples on visits and stay compliant."

OOTB Flow LWC

Short, status-driven, and Action Launcher is already on the Visit. OmniStudio is not justified.

Scenario B — Medical Science Liaison

"MSLs need a better way to log and route medical questions from HCPs."

OmniScript FlexCard Apex

Branching capture across Inquiry, Inquiry Question, and Answer, plus routing. OmniStudio earns its place here — and the reasoning is on the page.

Division of labour

What the agent handles, and what stays yours

The skill drafts. It does not decide. Everything in the right-hand column is a judgment call it will ask about rather than assume.

The agent handles
  • Detecting the workflow mode from your phrasing
  • Loading the right sub-domain object model and nothing else
  • Verifying component and object names, or marking them proposed
  • Scanning requirements/ for stories that overlap or conflict
  • Choosing the declarative-first build technology and stating why
  • Enumerating every field on every write
You still decide
  • Commercial, Medical, or Market Access — and net-new versus Veeva migration
  • The persona and the business outcome
  • Regulatory scope: sample accountability, consent, Open Payments
  • Which markets, product families, and account types are in scope
  • Whether the estimate is credible — the sizing is a starting point
  • Whether a proposed object name is the real one

Adopt & Maintain

One architect builds it. Every engagement benefits.

The pack is published once and installed everywhere, instead of each architect deriving the same LSC standard independently. The same mechanism a team already uses for shared libraries.

If you have seen one architect's delivery process, you have seen one architect's delivery process. When the persona contract, the object catalog, and the build-technology guide live in a shared repository, consistency stops depending on who staffed the engagement.

The pattern

Publish once, install everywhere

One owner maintains the pack; everyone else pulls it down. Two decisions gate this, and neither is technical.

Who owns it

One person maintains the skill for the competency — typically the delivery lead or a senior architect they nominate. The version history and the evaluation rubric live with that owner.

Where it lives

A shared repository, so it can be installed and updated rather than hand-copied. Ownership and location are the only real blockers — the build itself is one session.

Publishing, in three steps
1

Create the shared repository

Copy the finished skills/lsc-delivery-architect/ folder and the trigger rule into a repo your competency owns. Include the evaluations — they are how the next maintainer knows a change was safe.

2

Confirm the install works

Test it yourself in a fresh project, reload Cursor, and run the step 5 validation prompt. Verify the routing before you tell anyone it is ready.

3

Share the one-line command

Clone, copy, reload, run the validation prompt. That is the whole onboarding ask — no per-person setup session.

Working practices

Keep the skill generic and the engagement specifics local

Do

Keep engagement specifics — stakeholders, org constraints, which release you are targeting — in the project. Let the skill stay generic. Point at the skill; do not restate it.

Avoid

Do not fork the skill for one client. If a gap shows up, fix the shared reference so every future engagement benefits. Keep client names out of skills/ entirely.

Keep it healthy

Two maintenance prompts, on a cadence

The object catalog drifts with every release, and a reference edit can silently break a blocker. Both are cheap to check and expensive to discover late.

Per release — object catalog check
Prompt
Review the LSC standard-object catalog reference against the current API version. What objects or fields have been added, renamed, or deprecated since Summer '26 / v67.0?
Quarterly — run the evaluations
Prompt
Run each scenario in evaluations/ against this skill and score the output on every expected_behavior item. Report which blockers failed.

The evaluations are the source of truth for whether the skill still works. Extend them before you extend the documentation.

Optional grounding

Two indexes make verification stronger. Neither is required.

IndexWhat it verifiesIf it is missing
code-review-graph Custom components — callers, dependents, and the tests that cover them. Falls back to file search; unverifiable names are marked (proposed).
salesforce-docs Standard LSC objects, fields, and features, with citations. Falls back to the curated catalog reference and flags what it could not confirm.

The skill is explicit about what it could not verify — which is the behaviour you want when the alternative is a confident guess.
